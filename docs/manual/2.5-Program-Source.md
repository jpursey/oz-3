# Program Source

A program is written as assembly source: text files of instructions, data, and directives, which the OZ-3 assembler turns into a [program](2.4-Program-Files.md#programs) that can be loaded into memory and run. By convention a source file has the `.oza` extension. This page describes that source: how statements are written, how instructions are matched, and what the assembler produces.

The assembler knows no instruction of its own. A program is assembled for an instruction set, and each instruction is written as that instruction set's [source patterns](2.3-Instruction-Set-Source.md#arguments) say, so the same assembler works for the [default instruction set](2.2-Default-Instruction-Set.md) or any other. Everything else on this page (labels, directives, comments, and expressions) is the assembler's, and is the same for every instruction set.

Here is a program for the default instruction set that writes a zero terminated message to port 1:

    ; Writes a message to the console port, a word at a time.
    .CONST CONSOLE = 1
    .STACK 64

    start:
        MOV R1, message     ; MOV.LW: R1 is the message's address
    @next:
        MOV R2, (R1)        ; MOV.LW, the ($r) form
        TST R2              ; TST.W
        JC Z, @done         ; Z is the Condition value 4
        OUT CONSOLE, R2     ; OUT.IW: CONSOLE is the port number
        ADQ R1, 1
        JP @next
    @done:
        HALT

    message:
        .DW 'Hello', 0

### Assembling a program

A host application assembles a program with the functions in `oz3/tools/program_assembler.h`:

* **`AssembleProgramFile`:** Assembles the program whose main source file is at a path in a `gb::FileSystem`, along with the files it includes.
* **`AssembleProgram`:** Assembles a program from source text, which can't include files.

Each takes an `InstructionSetSyntax` (in `oz3/tools/instruction_set_syntax.h`), which holds every way an instruction set's instructions can be written. A host creates it once for an instruction set, and uses it for every program it assembles. The result is an `AsmProgram`, whose `Program` can be given straight to `ProgramLoader`, or written to a [program file](2.4-Program-Files.md). Its `GetBareProgram` gives the same program as a [bare program](2.4-Program-Files.md#bare-programs), or an error if it can't be one.

#### `oz3asm`

`oz3asm` is the command line assembler, which writes the program file:

    oz3asm [-i <instruction set>] [-b] [-m] [-l] <source file> [<program file>]

* **Program file:** The [program file](2.4-Program-Files.md), which by default is the source file's path with the extension `.oz3`.
* **`-i`, `--instruction-set`:** Assembles for the instruction set in an [instruction set source](2.3-Instruction-Set-Source.md) file (`.izm`), rather than the [default instruction set](2.2-Default-Instruction-Set.md).
* **`-b`, `--bare`:** Writes a [bare program](2.4-Program-Files.md#bare-programs) file rather than a program file, for a [default program](#the-default-program). It fails for a program that declares segments, one with a label in an address from `BS` or `BE` (see [Addresses](#addresses)), or one whose contents, rounded up to a multiple of two words, and stack pass 64 Kiw.
* **`-m`, `--map`:** Writes the program's map beside the program file, with the extension `.oz3map`. A debugger reads it to show where each word of the program came from, and its labels and constants.
* **`-l`, `--listing`:** Writes a listing beside the program file, with the extension `.oz3lst` (see [Listings](#listings)).

For example, `oz3asm -m -l programs/hello.oza` writes `programs/hello.oz3`, `programs/hello.oz3map`, and `programs/hello.oz3lst`. Paths are written the operating system's way, absolute or relative to the current directory. `oz3asm --help` (or `-h`) describes the arguments and flags. On success, `oz3asm` exits with 0. On failure, it prints the errors and exits with a nonzero code. A program with errors writes no files. Files from an earlier run are overwritten, but a command line that names one file for two things, such as a program file that is the source file, is an error.

#### Listings

A listing is text for people: every line of the source, with where its words are and what they are, to check what each statement became. Each source file is listed in turn under its path, the main file first, and each line is a row of a location, up to four words in hex, and the line itself:

    0000                       start:
    0000  03E1 000C                MOV R1, message     ; MOV.LW: R1 is the message's address
    0002                       @next:
    0002  034A                     MOV R2, (R1)        ; MOV.LW, the ($r) form
    ...
    000C                       message:
    000C  0048 0065 006C 006C      .DW 'Hello', 0
    0010  006F 0000

* **Locations** are a segment's name and an offset (`MAIN:0004`), or just the offset in the [default program](#the-default-program). A name of more than eight characters is cut to its first seven and a `~` (`INTERRU~:0004`).
* **A line of more than four words** carries on in more rows, each at the offset of its first word.
* **A line that writes no words** has no location, unless it defines a label, which has the label's location.
* **A file included more than once** has a row for each time a line was assembled, with the line's text in only the first.

A host application formats a listing itself with `FormatProgramListing`, or writes one to a file with `WriteProgramListingFile`, in `oz3/tools/program_listing.h`.

### Lines

A statement is one line: an optional label, then an optional instruction or directive, then an optional comment.

    loop:   ADD R1, 1       ; Adds 1 to R1.

* **Comments:** `;` starts a comment, which runs to the end of the line.
* **Labels:** A label is a name followed by `:` at the start of a line (see [Symbols](#symbols)). A label on a line of its own labels the next statement in its segment.
* **Directives:** A directive starts with `.`, with no space after it (`.DW`), where an instruction would be (see [Directives](#directives)). Instruction names can't start with `.`, so a directive never collides with an instruction.
* **Spacing:** Spaces and tabs are free within a line, but a statement can't go on to the next line.
* **Case:** Names are case-insensitive: instruction names, registers, the words an instruction's pattern writes literally, named values, directives, and symbols. `add r1, 5` is `ADD R1, 5`. Every name is turned to upper case as it is read. Strings and characters keep their case.

### Values

* **Numbers:** Decimal (`15`), hexadecimal with an `h` suffix (`0Fh`), or binary with a `b` suffix (`1111b`), with the suffix in either case (`0FFH`). A hexadecimal number starts with a digit, so it is `0FFh` and not `FFh`, which is a name. Numbers have no sign of their own: `-1` is `-` applied to `1`.
* **Strings:** The OZ-3 has no bytes, so a string is either one character per word, or two packed into each word, and the quotes say which:
  * `'Hello'` is one character per word: five words.
  * `"Hello"` is two characters per word, the first in the low byte, and the last word padded with a zero byte: `6548h 6C6Ch 006Fh`. On a host, where each word is two bytes, low byte first (as in [program files](2.4-Program-Files.md)), packed text reads in order.

  A quote inside a string is doubled (`'It''s'`). Source files are UTF-8, and a character is its Unicode code point, which must fit in a word (or a byte, for two per word).
* **Characters:** In an expression, a string that makes one word is that word: `'A'` is 65, and `"AB"` is `4142h`.
* **Registers:** `R0` to `R7`, `BC`, `BS`, `BD`, `BE`, `MB`, `IP`, `FP`, `SP`, and `D0` to `D3` are the [registers](2-Specifications.md), for every instruction set. They are reserved, so they can't be symbols, and are never part of an expression.

### Symbols

A symbol is a name for an integer. Names are C identifiers. There are three kinds:

* **Labels:** A label's value is the offset of the statement it labels: the number of words before it in its segment.
* **Local labels:** A local label starts with `@` (`@loop`), and is scoped from one label to the next, so every routine can have its own `@loop`. It can only be used in its scope. A local label before the first label is in the scope that starts the program. Scopes go on across included files, as if the files' text were where they are included.
* **Constants:** A constant is defined by `.CONST` as an expression (see [Constants](#constants)).

Symbols are global to the program, across included files, apart from local labels. A symbol is defined once, and can be used above or below where it is defined, except where a value must be known as the statement is read (see [Passes](#passes)).

A symbol can share its name with an instruction, as where a name is decides what it is: `ADD: ADD R1, 5`. It can also share its name with a word that an instruction's pattern writes literally, but it then collides wherever that pattern could match. In the default instruction set, `RST SELF, 1` matches only the `SELF` form, unless `SELF` is a symbol, in which case it matches the `$#3` form too, which is an error (see [Matching](#matching)).

### Expressions

An expression is integer arithmetic over numbers, characters, symbols, and `$` (the offset of the current statement), with C's operators and their precedence:

| Precedence | Operators                                                  |
| ---------- | ---------------------------------------------------------- |
| Highest    | Unary `-` (negate), `~` (bitwise not), `!` (logical not)   |
|            | `*`, `/`, `%`                                              |
|            | `+`, `-`                                                   |
|            | `<<`, `>>`                                                 |
|            | `&`                                                        |
|            | `^`                                                        |
| Lowest     | `\|`                                                       |

Operators of the same precedence apply from left to right, and parentheses group.

**Widths:** Where an expression is used sets its width: a word (16 bits) or a dword (32 bits). An expression is a word in a `$v`, a code word argument (a `$#` or a named value), `.DW`, and the directives' values, and a dword in a `$V` and `.DD`.

**The arithmetic is the machine's.** A value is its width's bits, and every operator works on them as the CPU would, with nothing wider underneath:

* `+`, `-`, `*`, and unary `-` wrap, as `ADD` does, so `-1` is `0FFFFh` as a word, and `65535 + 1` is 0. `A * B / C` divides whatever `A * B` wrapped to, as the same code would on the machine.
* `/` and `%` are unsigned, as `DIV` and `MOD` are, so `-2 / 2` is `7FFFh` as a word.
* `<<` and `>>` are logical, and a shift by the width or more gives 0.
* `~`, `&`, `|`, and `^` are bitwise, so `~0FF00h` is `00FFh` as a word. `!` is 1 for 0, and 0 otherwise.

A number, a character, and a symbol's value must fit the width, from 0 to its largest unsigned value, and dividing by zero is an error. A code word argument must also fit its bits.

**Low and high words:** `LOW(x)` and `HIGH(x)` are the low and high words of `x`, which is evaluated as a dword wherever they are used, so either half of a dword can be written where a word is used. With `.CONST ADDR = 12345h`, `.DW LOW(ADDR), HIGH(ADDR)` is `2345h 0001h`, as `.DD ADDR` writes it, but `.DW ADDR & 0FFFFh` is an error, as `ADDR` must fit a word there. Each is just a number, even of a label or `$`. `LOW` and `HIGH` are only these where `(` follows them, so they can still be symbols.

**Labels and `$`** are offsets in their segment (see [Segments](#segments)). One plus or minus a number is still an offset in its segment, and anything else on one is just a number, such as `end - start`, the distance between two labels in the same segment. Combining labels or `$` in two different segments, with any operator, is an error, as their offsets are from different places: `data_end - code_start` and `table + vars` mean nothing, but `vars + (table_end - table)` is `vars` plus a distance. A program with no `.SEGMENT` has one segment, so its labels can always be combined.

#### Constants

    .CONST <name> = <expression>

A constant is its expression, which is evaluated where the constant is used, in that width. So with `.CONST MASK = ~1`, `MASK` is `0FFFEh` as a word, and `0FFFFFFFEh` as a dword. A constant's own value is its value as a dword, which it must have even if it isn't used. A constant whose value depends on itself is an error.

`$` in a constant is the offset where the constant is defined, not where it is used, and its local labels are those of the scope it is defined in, so a constant means the same everywhere:

    table:
        .DW 1, 2, 3
    .CONST TABLE_SIZE = $ - table   ; 3, wherever TABLE_SIZE is used

An error in a constant's expression is reported once, where it is. A constant that has a value, but can't be evaluated as a word, is an error wherever it is used as one instead: with `.CONST BIG = 70000`, `.DD BIG` is fine, and `.DW BIG` is an error at the `BIG`.

### Instructions

An instruction is written as one of the instruction set's [source patterns](2.3-Instruction-Set-Source.md#arguments), after its name.

* **Names:** A full name (`ADD.W`) is that instruction, and a name without an extension (`ADD`) is every instruction with that name, with or without an extension (`ADD.W`, `ADD.D`, and `ADD.S`). The `.` has no spaces around it, or it isn't part of the name: `ADD .W` is `ADD` with the arguments `.W`.
* **Forms:** An instruction with a macro argument (`$m`) can be written as each of its macro's codes. `MOV.LW "$r, $m"` can be written as `MOV.LW R1, R2`, `MOV.LW R1, 5`, `MOV.LW R1, (R2)`, and the other codes of its macro. Each of these is a form of the instruction.

#### Matching

A statement is matched against every form of the instructions its name may be, token by token, so spacing doesn't matter:

* **Literal text** matches the same token, ignoring case for a word. A literal number matches any expression with that value, so in the default instruction set, `SETB R1, BIT` matches the form for bit 3 when `BIT` is 3.
* **`$r` and `$R`** match a register that the argument can hold: `$r` is `R0` to `R7`, `$r2` only `R0` to `R3`, and `$r4` adds `BC`, `BS`, `BD`, `BE`, `MB`, `IP`, `FP`, and `SP`. `$R` is `D0` to `D3`.
* **`$#`, named values, `$v`, and `$V`** match an expression, the longest one at that point. A pattern can't follow a value with a binary operator, so a value always ends at the pattern's next literal. A named value's names are in scope within its argument, ahead of a symbol of the same name, so a symbol named `C` never breaks `JC C, @done`.
* **Brackets are the pattern's.** A value can't be wrapped in parentheses as a whole: `JP (5)` doesn't match `JP $v`, which would quietly jump to 5 where the program meant the word at 5. Parentheses inside a value are fine (`(SP + (N + 1) * 2)`), and around a whole value they are never needed.

A statement must match exactly one form. Matching none is an error that lists the instruction's forms, and matching more than one is an error that lists those it matched, so the program says which it means: in the default instruction set, `PUSH 5` matches both `PUSH.W $v` and `PUSH.D $V`, so it is written `PUSH.W 5`. No form is preferred over another.

A form's code word arguments (`$#` and named values) and literal numbers must be known as the statement is read (see [Passes](#passes)), so they can only use symbols defined above the statement. A form only matches if they have values, and a literal number's value is its number.

Once a statement matches, each code word value must fit its bits, and its registers must keep the instruction's [register rules](2.3-Instruction-Set-Source.md#register-rules). Otherwise it is an error at the value or register at fault: for `instruction(distinct) MVI "($r), ($r)"`, `MVI (R1), (R1)` is an error at the second `R1`, as `MVI` can't use the same register for both addresses.

#### Encoding

The matched form gives the code word, with each argument encoded in its bits, followed by a word for each `$v`, and two for each `$V`, low word first. A `$v` is encoded by its [value type](2.3-Instruction-Set-Source.md#value-types): with none, as written; as an [address](#addresses) from a bank's base register; or as a relative target address, encoded as its offset from the next instruction, so `JPR @loop` jumps to `@loop`.

#### Addresses

A label is its offset in its own segment, but some address forms are offsets from a bank's base register, wherever that is. The instruction set marks these with a `code`, `stack`, `data`, or `extra` [value type](2.3-Instruction-Set-Source.md#value-types): in the default instruction set, they are `S(n)`, `D(n)`, and `E(n)` (and `S[n]`, `D[n]`, and `E[n]`), from `BS`, `BD`, and `BE`, and the target of `JP`, `JC`, `JD`, and `CALL`, from `BC`. A relative target address is in `CODE` too, as for `JPR`. The assembler makes a label in one of them address the label's word:

* **The segment:** A label in an address must be in the segment with that bank's role, or it is an error: `D(table)` needs `table` in the `DATA` segment, `S(counter)` needs `counter` in the stack segment, and `JP start` and `JPR start` need `start` in the code segment. The default program's one segment has every role, so any of its labels can be in any of them.
* **The stack:** `BS` is at the end of the stack segment, or of each instance's words in a per instance stack segment (see [Instances](#instances)), so a label in `S()` is encoded as its offset from there, which wraps. `S(counter)` reads `counter`, wherever the stack segment is, and however big it is.
* **The others:** `BC`, `BD`, and `BE` are at the start of their segments, or of each instance's words, so a label in an address from one of them is encoded as its offset, unchanged.
* **Expressions:** A label or `$`, or a constant that is one, plus or minus a number, is still an offset in its segment, so `D(table + 2)` is checked too. Anything else is just a number, which is never checked: `D(5)`, or `D(end - start)`, the distance between two labels (see [Expressions](#expressions)).

A label in an address is encoded for the base registers where loading the program starts them, for each instance. A program that moves one (`MOV BD, R1`), or a core started on it with other base registers, must allow for that, as the assembler can't know.

Only these are checked. A label written as a value, such as in `MOV R1, table` before `MOV R2, (R1)`, is just its offset, and the program must make sure it is an address from the right base register, as the assembler can't follow a value into a register.

### Directives

| Directive                | Meaning                                                               |
| ------------------------ | --------------------------------------------------------------------- |
| `.INCLUDE "<path>"`      | The statements of another source file, as if its text were here.      |
| `.CONST <name> = <expr>` | Defines a constant (see [Constants](#constants)).                     |
| `.DW <item>, ...`        | Writes a word for each expression, and a string's words for a string. |
| `.DD <item>, ...`        | Writes a dword for each expression, low word first.                   |
| `.DS <count>`            | Reserves `count` words, without writing them.                         |
| `.STACK <words>`         | The words of stack the program needs.                                 |
| `.SEGMENT <name> [...]`  | Switches to a segment (see [Segments](#segments)).                    |
| `.BANK <name>[, <mask>]` | Declares a bank (see [Banks](#banks)).                                |
| `.INSTANCES <count>`     | How many instances the program has (see [Instances](#instances)).     |

* **`.INCLUDE`:** The path is relative to the file that includes it. A file can be included more than once, but including a file that is already being included is an error, as it would never end.
* **`.DW`:** A string on its own is its words (see [Values](#values)), so a zero terminated string is `.DW 'Hello', 0`, or packed, `.DW "Hello", 0`. Anything else is an expression, so `.DW 'A' + 1` is one word. Any item of `.DW` or `.DD` can start with `SIZE(<n>)` (see below).
* **`SIZE`:** An item of `.DW` or `.DD` with `SIZE` starts a field of that many words or dwords, for data of a fixed size. The field holds that item and the ones after it, up to the next item with `SIZE` or the end of the directive, and then zeros: `.DW SIZE(8) "A.TXT"` is `2E41h 5854h 0054h` and five zero words, `.DW SIZE(6) "HELLO", SIZE(2) "TXT"` is a six-word field and a two-word field, as in a [disk name](3.5-Disk-Drive.md#names-and-patterns), and `.DD SIZE(2) 1` is the dwords 1 and 0. Items before the first `SIZE` are only their own words, as in a directive with none (`.DW 1, SIZE(2) 2` is 1, 2, and 0). Items that fill a field exactly have no zeros, and an item that passes its end is an error. Each size must be known as the statement is read. `SIZE` is only this where `(` follows it, so a symbol can still be named `SIZE` (`.DW SIZE`).
* **`.DS`:** Reserved words are not part of the program's data, so the loader doesn't write them, and they hold whatever was in memory. This is how variables cost nothing in the program file. The count must be known as the statement is read.
* **`.STACK`:** A program with a stack segment gives its size once, in words, which is each instance's. Every program that runs has a stack, as every `CALL`, `PUSH`, and interrupt uses it. The size must be known as the statement is read.

### Programs

A [program](2.4-Program-Files.md#programs) is made of segments, each holding the words its statements assemble to, from offset 0. A segment's data is each run of words the program writes, in blocks aligned to two words. Where a program writes only one word of an aligned pair, the other is written as 0.

A program has one instance, unless it declares more (see [Instances](#instances)), whose base registers start at their segments: `BC`, `BD`, and `BE` at the start, and `BS` at the end. Its segments are in one bank, which may be any physical bank, unless it declares its banks (see [Banks](#banks)).

#### The default program

A program that declares no segments is one RAM segment, placed anywhere, with all four roles:

* **Code and data** start at offset 0, so the program starts at its first statement, as resetting a core sets `IP` to 0.
* **The stack** grows down from the end of the segment, as `SP` starts at 0, and the first push wraps it to the last word.
* **Its size** is its contents and its stack (`.STACK`), rounded up to whole pages (4 Kiw each). So it needs no more memory than it uses, and loads into a bank of any size with room. Contents and stack can't pass 64 Kiw, the size of a bank.

This is the simplest program to write: instructions, data, and `.STACK`. `oz3asm --bare` writes it as a [bare program](2.4-Program-Files.md#bare-programs), which loads at any word of a bank rather than on whole pages, with its contents rounded up to a multiple of two words and its stack after them. Starting it leaves `BE` as it is, rather than at the program's start, so a program that uses `BE` sets it itself, and `BS` is at the end of its stack words rather than of its pages, so a bare program can't have a label in `S()` or `E()` (use `D()`, as the one segment has every role). Its map and listing are the same either way, as its offsets are.

#### Segments

    .SEGMENT <name> [<attribute> ...]

Statements assemble into the current segment, which `.SEGMENT` switches to, declaring the segment the first time with its attributes. A later `.SEGMENT` of the same name only switches back to it, and can't give attributes, so a segment's statements can be written in several places, and in several files. Segment names are their own, so a segment can share its name with a symbol.

* **Before the first `.SEGMENT`:** Nothing can be in a segment before the first `.SEGMENT`: no label, and no statement that writes or reserves words. Constants and `.STACK` can be there. A `$` there is 0, as nothing is written before it, and is in no segment once segments are declared, so it is just the number 0, which no address checks.
* **Labels and `$`** are offsets in the segment they are in (see [Expressions](#expressions) and [Addresses](#addresses)).
* **Roles:** The attributes `CODE`, `STACK`, `DATA`, and `EXTRA` give the segment that role, so a core starting the program sets that bank (and its base register, `BC`, `BS`, `BD`, or `BE`) to the segment. A segment can have several roles, or none, and each role is at most one segment's. A role no segment has is left as it is when the program is loaded, as for a data only program, which has no code.
* **The program starts** at offset 0 of its code segment.
* **The stack** grows down from the end of the stack segment, after its contents. A program with a stack segment needs `.STACK`, and one without can't have it.
* **Sizes:** A segment's size is its contents, and the stack segment's its stack too, rounded up to whole pages, unless `PAGES` gives it. It can't pass 64 Kiw.
* **Order:** The segments are in the program in the order they are declared.

A segment's other attributes say where it goes. Without them, it is RAM, placed anywhere in its bank:

| Attribute    | Meaning                                                                           |
| ------------ | --------------------------------------------------------------------------------- |
| `ROM`        | The segment is read-only, so it can be loaded into ROM (or RAM, if ROM is short). |
| `PAGE(n)`    | The segment starts at page `n` of its bank (0 to 15).                             |
| `PAGES(n)`   | The segment is `n` pages (1 to 16).                                               |
| `BANK(name)` | The segment is in the bank `name` (see [Banks](#banks)).                          |
| `INSTANCE`   | Each instance has its own words of the segment (see [Instances](#instances)).     |

* **`PAGE` and `PAGES`** take an expression in brackets, so it has a clear end, which must be known as the statement is read (see [Passes](#passes)).
* **`PAGES`** must be at least what the segment's contents (and stack) need. Any more is at the end of the segment, so in the stack segment, the stack gets it.
* A segment with `PAGE` can't pass the end of the bank, at page 16.
* Each attribute is given at most once.

The example at the top of this page, with its code, message, and stack in segments of their own:

    .CONST CONSOLE = 1
    .STACK 64

    .SEGMENT main CODE
    start:
        MOV R1, message     ; R1 is the message's address in DATA
    @next:
        MOV R2, (R1)
        TST R2
        JC Z, @done
        OUT CONSOLE, R2
        ADQ R1, 1
        JP @next
    @done:
        HALT

    .SEGMENT strings DATA ROM
    message:
        .DW 'Hello', 0

    .SEGMENT stack STACK

The message never changes, so its segment is ROM. The stack segment has no contents, so it is one page, holding the 64 words of `.STACK`.

#### Banks

    .BANK <name>[, <mask>]

A program's segments are in one bank, which may be any physical bank, unless it declares its banks with `.BANK`. Then each segment is in one of them, with `BANK(<name>)`, so a program can have more than a bank's 16 pages, or keep segments in the physical banks a machine has for them, such as its video memory:

    .CONST VRAM0 = 1 << 2
    .CONST VRAM1 = 1 << 3
    .BANK video, VRAM0 | VRAM1
    .BANK main

    .SEGMENT code CODE BANK(main)
        ...
    .SEGMENT screen EXTRA BANK(video) PAGES(2)

* **The mask** has a bit for each physical bank (0 to 15) the bank may be loaded into, so `VRAM0 | VRAM1` is banks 2 and 3. Without one, it is `0FFFFh`, any bank. It must have at least one bit, and must be known as the statement is read.
* **Every segment** names its bank with `BANK`, and the bank can be declared before or after the segment.
* **Order:** The banks are in the program in the order they are declared. The loader assigns them from first to last, so a bank with a narrower mask goes first.
* Bank names are their own, so a bank can share its name with a symbol or a segment. A program has at most 16 banks.

#### Instances

    .INSTANCES <count>

A program's instances are how many cores may run it at once, as an operating system might run a program it loaded once as several processes. A program has one instance unless `.INSTANCES` gives the count, from 1 to 8, which must be known as the statement is read.

Each instance has its own offsets for the base registers, so it can have its own stack and variables, while sharing code, constant data, and anything else the program shares. A segment is shared by every instance, or with `INSTANCE`, per instance:

* **Shared:** Every instance's offset is 0: code and data from the segment's start, and the stack down from its end.
* **Per instance:** The segment's statements describe one instance's words, so its labels are offsets within them. The segment holds those words for every instance in turn, and each instance's offset is the start of its own words, so the same labels work for every instance. Its size is one instance's words (and stack, in the stack segment) times the number of instances, rounded up to whole pages, unless `PAGES` gives more.
* **The stack** is at the end of each instance's own words in a per instance stack segment. With more than one instance, the stack segment must be per instance, or the instances would share one stack.
* **Code** is always shared, so a segment can't have both `CODE` and `INSTANCE`.
* **A per instance segment can only reserve words** (`.DS`), never write them. The loader writes a program's words once, so only one instance would get them, and they would only be fresh once anyway: an instance that runs again finds what the last run left. Each instance sets up its own variables, and initialized tables go in a shared segment.

The default program's one segment is shared, and holds the stack, so a program with more than one instance declares its segments:

    .INSTANCES 4
    .STACK 64

    .SEGMENT main CODE
        ...
    .SEGMENT tables DATA ROM
        ...
    .SEGMENT vars EXTRA INSTANCE
    count:
        .DS 1
    .SEGMENT stack STACK INSTANCE

Each of the four instances has its own `count` and its own 64 words of stack, while they share the code and the tables.

### Passes

The assembler makes two passes over the source:

1. **Layout:** Reads every statement, matches each instruction to its form, and so gives every statement its offset, and every label its value.
2. **Encoding:** Evaluates every expression, now that every symbol is defined, and writes the words.

Anything that decides a statement's form or size is used in the first pass, so it must be known when the statement is reached: a code word argument, a literal number in a pattern, the values of `.DS` and `.STACK`, the `SIZE` of `.DW` and `.DD`, a segment's `PAGE` and `PAGES`, a bank's mask, and `.INSTANCES`. A symbol used there must be defined above it, as must the symbols of a constant used there. Everywhere else (`$v`, `$V`, `.DW`, and `.DD`), symbols may be defined later.

### Errors

Errors give the file, line, and column. The assembler reports every error in a pass, rather than only the first, as each statement is one line and an error in one doesn't confuse the next. A pass stops after 100 errors, with a last error saying so. A pass with errors is the last one, as the second pass's errors would mostly follow from the first's, and a source with errors produces no program.
