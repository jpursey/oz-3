# Timer

A periodic interrupt, and a port that tells a program the cycle count, the time since power on, and the host's date and time. It is what programs pace themselves with.

### Wiring and settings

The timer is wired to 2 consecutive ports, the **tick port** and then the **clock port**, and one interrupt line on the cores it is connected to. It has no memory (see [Wiring and settings](3-Devices.md#wiring-and-settings)).

| Setting   | Default | What                       |
| --------- | ------- | -------------------------- |
| `tick_hz` | 60      | Ticks a second: at least 1 |

### Ticks

* **The schedule:** tick `n` is at cycle `n * clock_hz / tick_hz`, so ticks don't drift where one isn't a whole number of cycles. At 1 MHz, 60 Hz is a tick every 16,666 or 16,667 cycles.
* **At each tick**, the timer writes the ticks since power on to the tick port, as a dword with the low word first (the low 32 bits of the count), sets the port's status, and raises its interrupt.
* **Reading:** `INS` reads the tick port only when a tick has passed since it was last read, so a program with no handler can wait for the next tick with an `INS` loop. `IN` reads the count whatever the status.
* **Timing:** a tick waits while a core holds the tick port, and one that waited doesn't delay the next, so a tick missed this way comes a cycle after the one before it. There is at most one tick in a cycle.

### The clock port

A program asks the clock port for something by writing its **index** to port word 0 with `OUT`, which sets the status. The cycle after, the timer takes the index, clearing the status, and writes its answer to the port as a dword, where `IN` reads it. The timer requests the port's lock before the next instruction can, so an `IN` right after the `OUT` reads the answer. With the clock port on port 4:

```
OUT.IW 4, 0       ; Ask for the cycle count
IN 4, D0          ; and read it
```

| Index | Answer                                                                                                                   |
| ----- | ------------------------------------------------------------------------------------------------------------------------ |
| 0     | The cycle count: its low 32 bits                                                                                         |
| 1     | The milliseconds since power on: their low 32 bits                                                                       |
| 2     | The host's date: word 0 the year, and word 1 the month (1 to 12) in the high byte and the day (1 to 31) in the low byte |
| 3     | The host's time: word 0 the hour (0 to 23), and word 1 the minute in the high byte and the second in the low byte        |
| Other | 0                                                                                                                        |

* **The cycle count** is the processor's when the timer answers, which is the cycle after the `OUT` wrote the index, unless the timer waited for the port. It is for timing short things, in cycles as `WAIT` is, since it wraps: in a little over an hour at 1 MHz.
* **Milliseconds** are the machine's time, not the host's: the cycle count at the clock rate, rounded down. So they are the same at any clock rate, and run fast or slow with the machine. They wrap after about 49 days.
* **The date and time** are the host's, to the second, in the time zone it wants programs to see. The timer asks the host's clock for them each time a program asks for the time, so they are always current. The clock is the host's local time unless the host gives another, and a host that gives an empty one gets zeros for both, which means no date, since month 0 is invalid. A year outside 0 to 65535 reads as its low 16 bits. They have nothing to do with the cycle count, ticks, or milliseconds, which are the machine's: when a host can't run the machine at its clock rate in real time, or runs it faster, the date and time drift from them, so a program never times anything with them.
* **Asking for the time latches the date and time,** and asking for the date answers with the date latched by the last time, or zeros before the first. So a program that wants only the time asks once, and one that wants both reads the time and then the date, and the two always go together, even across midnight.
* **One question at a time:** a core that writes an index while another core's is still waiting for the timer replaces it, and both read the answer to the second. So cores that share the timer take turns asking.
* **Reading the index back** before the timer takes it, with `IN` or `INS`, takes the question back, and the timer doesn't answer.
