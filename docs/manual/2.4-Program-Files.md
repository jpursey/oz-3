# Program Files

A program file holds one program, ready to load into memory and run. It is the OZ-3's executable format, as `.COM` and `.EXE` files were for CP/M and DOS, so a program can be assembled once and loaded many times. By convention the file has the `.oz3` extension.

The OZ-3 has no bytes, so a program file is a sequence of 16-bit words, as an OZ-3 program would read them from a storage device. A loader written in OZ-3 code, such as an operating system's, reads it as easily as a host application does, so the format is part of the [specification](2-Specifications.md).

### Programs

A program describes the memory it needs and how a core starts running it. It needs no relocation: a loader only allocates pages, copies words, and sets base registers. A program has:

* **Banks:** The program's own memory banks, which the loader assigns to physical banks. Each has an *assign mask*, with a bit for each physical bank (0 to 15) it may be assigned to. Two program banks may be assigned to the same physical bank.
* **Segments:** Ranges of whole pages (4 Kiw each) in one of the program's banks, each with:
  * Its *bank*: the index of one of the program's banks.
  * Its *access*: read-only (ROM), or read-write (RAM). A read-only segment may be loaded into read-write pages if there aren't enough read-only ones.
  * Its *page start*: the page it must start at (0 to 15), or `FFFFh` to start at any page.
  * Its *page count*: the number of pages (1 to 16).
  * Its *data*: blocks of words to write into the segment, each at an offset from the segment's start, in order of offset. Each block's offset and size are multiples of two words, and no block is empty, so a loader can copy them two words at a time. Words outside every block are not written, so they hold whatever was already in memory.
* **Roles:** The segment, by index, that each of a core's banks (`CODE`, `STACK`, `DATA`, and `EXTRA`) is set to when it starts the program, or `FFFFh` to leave that bank as it is.
* **Instances:** One for each core that may run the program at the same time, each with an offset for each role's base register:
  * `BC`, `BD`, and `BE` start at the start of their segment, plus the offset.
  * `BS` starts at the end of its segment, minus the offset, as the stack grows down from `BS`.

  A program with no instances is data only, and no core starts it.

A program is valid to load if:

* It has at most 16 banks, 256 segments, and 8 instances.
* Each segment's bank is one of the program's banks, and a segment with a fixed page start fits in the bank (its page start plus page count is at most 16).
* The segments of one bank have at most 16 pages between them, and those with a fixed page start don't overlap.
* Each data block is aligned to two words, isn't empty, and fits in its segment.
* A segment's data blocks are in order of offset, and don't overlap.
* Each role is a segment of the program, or `FFFFh`.
* Each instance's offset for a role is at most the size of that role's segment, in words.

The loader also needs free pages, in a physical bank that the assign mask allows, for every program bank.

### File format

Every field is one word, and so is every count. The file has six parts, in this order:

| Part      | Words                                                                                                                   |
| --------- | ----------------------------------------------------------------------------------------------------------------------- |
| Header    | The identifier, `5A4Fh`, then the version of the format, `1`.                                                           |
| Banks     | The number of banks, then each bank's assign mask.                                                                      |
| Segments  | The number of segments, then five words for each: its bank, access, page start, page count, and number of data blocks. |
| Roles     | Four words: the `CODE`, `STACK`, `DATA`, and `EXTRA` segments.                                                          |
| Instances | The number of instances, then four words for each: its `BC`, `BS`, `BD`, and `BE` offsets.                              |
| Data      | Each segment's data blocks, in segment order, each as its offset and its size in units, and then its words.             |

Access is `0` for read-only and `1` for read-write.

A data block's offset and size are counted in *units* of two words, so a block at offset 10h of 6 words is written as `0008 0003`, followed by its 6 words. An offset is at most `7FFFh` units, the last unit of a bank, and a size is at least 1 unit, so a loader's copy loop never has to check for an empty block. A block can be as big as a whole bank, which is 8000h units.

Everything a loader needs to place the program comes before the data, and every segment's entry is the same size. So a loader can allocate every segment, or give up, before it writes any memory, and then copy each block straight from the device to where it goes.

The file ends after the last data block. A version of the format that adds anything has a new version number, which a loader for this version rejects.

For example, here is a program in one bank, with two segments: two pages of ROM at any page, holding four words of code, and one page of RAM for its stack and data. It has one instance, whose `BD` starts 100h words into the RAM segment.

    5A4F 0001                       Header
    0001 FFFF                       1 bank, any physical bank
    0002                            2 segments
    0000 0000 FFFF 0002 0001          Bank 0, ROM, any page, 2 pages, 1 block
    0000 0001 FFFF 0001 0000          Bank 0, RAM, any page, 1 page, no blocks
    0000 0001 0001 FFFF             CODE, STACK, and DATA roles, no EXTRA
    0001                            1 instance
    0000 0000 0100 0000               BC, BS, BD, and BE offsets
    0000 0002 1234 5678 9ABC DEF0   Code segment's block: offset 0, 2 units

### Files on a host

On a host, each word is two bytes, low byte first, so a program file starts with the bytes for "OZ".

A host application reads and writes program files with the functions in `oz3/tools/program_file.h`: `WriteProgramFile` and `ReadProgramFile` for files, and `WriteProgramWords` and `ReadProgramWords` for words in memory. Each holds the program as a `Program` (`oz3/tools/program.h`), which is what `ProgramLoader` (`oz3/tools/program_loader.h`) loads. `ValidateProgram` in `oz3/tools/program.h` checks that a `Program` is valid, by the rules in [Programs](#programs). A program file only ever holds a valid program, so writing a program that isn't valid fails, as do reading and loading one.

### Bare programs

A bare program is a [default program](2.5-Program-Source.md#the-default-program), one that declares no segments, with none of a program file's page structure: one block of memory, with its contents (its code and data) from the start and its stack after them, which a loader can place at any word of a bank rather than on a page. It is smaller and simpler to load than a program file, so it suits code that loads other code, such as a disk's boot loader, and the operating system it loads straight after itself. `oz3asm --bare` writes one (see [Program Source](2.5-Program-Source.md#oz3asm)).

By convention a bare program file also has the `.oz3` extension, but it is a format of its own, with its own identifier rather than a version of the program file's. Each format changes its version on its own, and a reader of either format rejects the other's files as what they are.

Every field is one word. The header is six words, and every part after it is whole dwords, so a loader can read the whole file two words at a time:

| Words | What                                                                                                            |
| ----- | --------------------------------------------------------------------------------------------------------------- |
| 0     | The identifier, `424Fh`                                                                                         |
| 1     | The version of the format, `1`                                                                                  |
| 2     | The size of its contents, in words                                                                              |
| 3     | The size of its stack, in words                                                                                 |
| 4     | The number of data blocks                                                                                       |
| 5     | Reserved, `0`                                                                                                   |
| 6...  | Each data block, in order of offset, as in a program file: its offset and its size in units, and then its words |

A bare program is valid if:

* Its contents are a multiple of two words, and its contents and stack together are at most 64 Kiw, the size of a bank.
* Each data block is aligned to two words, isn't empty, and ends within the contents.
* Its data blocks are in order of offset, and don't overlap.
* The reserved word is 0.

A loader places a bare program at an address, b, in a bank with room for its contents and stack from b:

* **Loading** copies each block's words to b plus the block's offset. Words outside every block, such as those `.DS` reserves, are not written, so they hold whatever was already in memory.
* **Starting** a core on it sets `BC` and `BD` to b, and `BS` to b plus its contents and its stack, so the stack grows down from the end of the program, with `SP` 0. `IP` starts at 0, the program's first statement. `BE` is left as it is.

For example, this program assembles to 6Ch words of contents, in three blocks, with 64 words of stack after them:

    .STACK 64
        NOP
        .DS 3
        .DW 1, 2
        .DS 100
        .DW 1234h, 5678h

    424F 0001 006C 0040 0003 0000   Header: 6Ch words of contents, 40h of stack, 3 blocks
    0000 0001 0000 0000             Offset 0, 1 unit: NOP, and a word not written
    0002 0001 0001 0002             Offset 4, 1 unit
    0035 0001 1234 5678             Offset 6Ah, 1 unit

On a host, as with a program file, each word is two bytes, low byte first, so a bare program file starts with the bytes for "OB". A host application reads and writes bare program files with the functions in `oz3/tools/program_file.h`: `WriteBareProgramFile` and `ReadBareProgramFile` for files, and `WriteBareProgramWords` and `ReadBareProgramWords` for words in memory. Each holds the program as a `BareProgram` (`oz3/tools/bare_program.h`), and `ValidateBareProgram` there checks that one is valid, by the rules above. A bare program file only ever holds a valid bare program, so writing one that isn't valid fails, as does reading one.
