# Disk Drive

A smart disk drive in the spirit of the Commodore 1541: it owns the file system on its disk, and a program talks to it in files, not sectors. It is meant to be driven by the OS, which issues every command and moves every word, through three ports: a **command port** for commands and their results, a **data port** for the words of a file, and a **control port** that shows the drive's state and resets it. The drive raises its interrupt when a command that needed the disk completes.

The disk is an image file on the host, which the host inserts and ejects while the machine runs. The drive trusts software and enforces no ownership, as era hardware did.

### Wiring and settings

The drive is wired to 3 consecutive ports, the command port, the data port, and then the control port, and one interrupt line on the cores it is connected to. It has no memory (see [Wiring and settings](3-Devices.md#wiring-and-settings)).

| Setting               | Default   | What                                                                                                |
| --------------------- | --------- | --------------------------------------------------------------------------------------------------- |
| `slots`               | 4         | How many files can be open at once: 1 to 255                                                        |
| `read_cache_sectors`  | 4         | Sectors in the drive's read cache, or 0 for none                                                    |
| `read_words_per_sec`  | Preset    | Words a second read from the disk                                                                   |
| `write_words_per_sec` | Preset    | Words a second written to the disk                                                                  |
| `cache_words_per_sec` | 1,000,000 | Words a second copied out of the read cache                                                         |
| `latency`             | Preset    | The time a transfer that isn't continuous with the one before costs first: a seek. At most a minute |

A rate of 0 takes no time. The drive has no drive letter, which is the machine's concept, and no disk until the host inserts one. The [Ozzy](4-Ozzy-Computer.md#devices) has up to four, `A:` to `D:`. A host can give it a clock for stamping files, as the [timer](3.4-Timer.md)'s, and a drive with no clock stamps zeros, which mean no date.

#### Timing presets

A machine can give a drive a preset for its rates, latency, and read cache, and change any of them. Real drives varied a lot with controller, interleave, and model, so these are rough approximations of typical effective speeds, not any specific drive. The default is the 1.44 MB floppy.

| Preset                                  | Disk size | Read rate | Write rate | Latency |
| --------------------------------------- | --------- | --------- | ---------- | ------- |
| 5¼″ 360 KB double-density floppy (1981) | 180 Kiw   | 8 Kiw/s   | 6 Kiw/s    | 150 ms  |
| 3½″ 720 KB double-density floppy (1986) | 360 Kiw   | 10 Kiw/s  | 8 Kiw/s    | 120 ms  |
| 3½″ 1.44 MB high-density floppy (1987)  | 720 Kiw   | 20 Kiw/s  | 16 Kiw/s   | 100 ms  |
| 10 MB hard disk, PC/XT class (1983)     | 5 Miw     | 40 Kiw/s  | 40 Kiw/s   | 85 ms   |
| 20 MB hard disk (1984)                  | 10 Miw    | 64 Kiw/s  | 64 Kiw/s   | 65 ms   |
| 40 MB hard disk, AT class (1986)        | 20 Miw    | 128 Kiw/s | 128 Kiw/s  | 40 ms   |

* **Rates** are sustained transfer rates, after interleave and rotation.
* **Latency** is a typical average access: a seek plus half a rotation.
* **The read cache** is 4 sectors for every preset, copied out at 1,000,000 words a second: a 1 MHz controller copying a word a cycle. It is small next to any disk, but not free.
* **The disk size** is the matching size for a new disk. The drive takes its size from the disk, so a preset doesn't limit which disks it reads.
* At 1 MHz, an OS streaming a file a word at a time moves roughly 100 Kiw/s, or about twice that with packed transfers. The floppies are far slower than the processor, while the fastest hard disks approach its limits, much as on real machines of the time.

### The disk

A disk is a flat array of sectors, all of the size its image gives (see [Images](#images)), numbered from 0. Every size, position, and length on the disk and in the drive's commands is in words: the OZ-3 has no byte addressing. A dword is two words, low word first. Packed text is two characters a word, the first in the low byte.

#### Images

On the host, a disk is an image file: an 8-word header, then the sectors in order, each word two bytes, low byte first, as in [program files](2.4-Program-Files.md). So sector `n` starts at byte 16 + 2 × sector size × `n`. The header describes the medium, and is never visible to the OZ-3 as data.

| Words | Field        | What                                    |
| ----- | ------------ | --------------------------------------- |
| 0, 1  | Image ID     | `"OZDK"` packed: 5A4Fh, 4B44h           |
| 2     | Version      | 1                                       |
| 3     | Sector size  | In words: 256                           |
| 4, 5  | Sector count | A dword: 1 to 4,194,433                 |
| 6     | Flags        | Bit 0: write-protected. Others reserved |
| 7     | Reserved     |                                         |

* **The sector size** is always 256 words in version 1. It is recorded so another size remains possible in a later version, and the rest of this page gives sizes in terms of it.
* **Write protection** belongs to the medium, like a floppy's notch. A read-only image file on the host is always write-protected.
* **A blank image** is all zero sectors: an unformatted disk.
* **The most sectors** a file system uses is 4,194,433, so a bigger disk can't be formatted.

#### Layout

A formatted disk is the superblock in sector 0, then the FAT in sectors 1 to F, then the clusters. The file system allocates in clusters of 2<sup>k</sup> sectors (1 to 64), set when the disk is formatted, so 16-bit cluster numbers cover small floppies and large hard disks alike. Clusters are numbered from 1, and cluster `n` starts at sector 1 + F + (`n` − 1) × sectors per cluster.

For example, at version 1's sector size:

| Disk              | Sectors | Sectors per cluster | Clusters | FAT sectors |
| ----------------- | ------- | ------------------- | -------- | ----------- |
| 360 KB floppy     | 720     | 1                   | 716      | 3           |
| 720 KB floppy     | 1,440   | 1                   | 1,433    | 6           |
| 1.44 MB floppy    | 2,880   | 1                   | 2,867    | 12          |
| 10 MiB hard disk  | 20,480  | 1                   | 20,399   | 80          |
| 20 MiB hard disk  | 40,960  | 1                   | 40,799   | 160         |
| 40 MiB hard disk  | 81,920  | 2                   | 40,879   | 160         |
| 128 MiB hard disk | 262,144 | 4                   | 65,471   | 256         |

A format picks the fewest sectors per cluster that cover the whole disk within 65,534 clusters, unless it is given a number, and the most clusters that fit after the superblock and FAT. At most a few sectors are left over. With 64 sectors a cluster, the format reaches about 1 Giw (2 GiB).

#### Superblock

The superblock is words 0 to 31 of sector 0. The rest of the sector is the boot area, 0 for now.

| Words | Field               | What                                                                                          |
| ----- | ------------------- | --------------------------------------------------------------------------------------------- |
| 0, 1  | Format ID           | `"OZFS"` packed: 5A4Fh, 5346h                                                                 |
| 2     | Version             | 1                                                                                             |
| 3     | Sectors per cluster | A power of two, 1 to 64                                                                       |
| 4     | Cluster count       | 1 to 65,534                                                                                   |
| 5     | FAT sectors         | At least (cluster count + 1) ÷ sector size, rounded up, and at most what 65,534 clusters need |
| 6     | Root cluster        | The root directory's first cluster                                                            |
| 7     | Flags               | Reserved                                                                                      |
| 8–15  | Volume label        | Packed text of 0 to 16 characters from the name set, zero-padded                              |
| 16–19 | Formatted           | The date and time it was formatted (see [Timestamps](#timestamps))                            |
| 20–31 | Reserved            |                                                                                               |

A disk is unformatted if its format ID or version is unknown, or its fields are out of range or don't fit the disk. No count of free clusters is stored, as it would go stale after a crash (see [The free count](#the-free-count)).

#### FAT and free list

The FAT is one word per cluster number. Files and the free list are all chains of clusters, which follow the same rules, so a FAT of all zeros is a free list of every cluster.

| Word    | Value | Meaning                                                        |
| ------- | ----- | -------------------------------------------------------------- |
| 0       | 0     | The free list starts at cluster 1                              |
| 0       | `n`   | The free list starts at cluster `n`                            |
| 0       | FFFFh | No free clusters: the disk is full                             |
| `n` ≥ 1 | 0     | Next is cluster `n` + 1, or the end if `n` is the last cluster |
| `n` ≥ 1 | `m`   | Next is cluster `m`                                            |
| `n` ≥ 1 | FFFFh | The end of this chain                                          |

Word 0 is the link of an imaginary cluster 0, so the same rule gives the free list's head. Whether a cluster is free depends only on which chain reaches it. There is one FAT and no copy.

* **Allocating** takes the free list's head, and writes the cluster's own entry, so a 0 never survives on a cluster in use.
* **Freeing a chain** links its last cluster to the old head, and makes its first cluster the new head.
* **Formatting** zeros the FAT, and gives cluster 1 to the root directory.

#### Directories

A directory is a chain of 16-word entries, packed into its sectors. The root directory is the only one for now, starting at the superblock's root cluster, and its size is its chain's full length. A directory with no free entry grows by a cluster, and directories never shrink.

| Words  | Field         | What                                                                                 |
| ------ | ------------- | ------------------------------------------------------------------------------------ |
| 0–7    | Name          | The name and extension (see [Names and patterns](#names-and-patterns))               |
| 8      | Attributes    | Bit 0 read-only, bit 1 hidden, bit 2 a directory (always 0 for now). Others reserved |
| 9      | First cluster | 0 for an empty file                                                                  |
| 10, 11 | Size          | A dword, in words                                                                    |
| 12–15  | Modified      | The date and time it was last written (see [Timestamps](#timestamps))                |

* **Free entries** have a first word of 0, so a cluster of zeros is all free entries.
* **Entries never move:** an entry stays in its place for its file's life, so a listing in progress stays valid while files are created or deleted.
* **Files:** a file of `s` words has exactly ⌈`s` ÷ cluster size⌉ clusters in its chain, and an empty one has first cluster 0 and no chain.
* **Names are unique** within a directory.
* **Hidden** is for the OS: the drive lists a hidden file like any other.

#### Timestamps

A date and time is four words, as the [timer](3.4-Timer.md#the-clock-port) answers them: the year, then the month in the high byte and the day in the low, then the hour, then the minute in the high byte and the second in the low. So the four words compare in order chronologically, and a program can copy the timer's straight in. All zeros is no date, since month 0 is invalid.

The drive stamps a file with its clock when it creates it, and again when it commits it after a write (see [Committing](#committing)), so a file written in many commands gets one stamp.

#### Names and patterns

A name is two packed fields, a 1 to 12 character name in words 0 to 5 and a 0 to 4 character extension in words 6 and 7, each zero-padded. No dot is stored: it exists only in display, such as `HELLO.TXT`, and in text a program parses. The same 8-word field is in directory entries and in the drive's commands. In assembly, a name is two directives, `.DW SIZE(6) "HELLO"` then `.DW SIZE(2) "TXT"`.

* **Characters** are letters, digits, and the punctuation ``! # $ % & ' ( ) - @ ^ _ ` { } ~``. Letters are stored in upper case, and names match without regard to case. `.`, `/`, `\`, and spaces are never in a name.
* **Padding** is zero bytes, and no zero byte comes before a character within a field.
* **Order:** names sort by their 16 bytes in order. As the first character of each pair is the low byte, the words don't sort as they are, but [`CMPT`](2.2-Default-Instruction-Set.md#cmpt) compares packed text in reading order, one instruction a word.

A **pattern** is a name that may also hold `?` and `*`, matched against each field separately, byte by byte. `?` matches any one byte, padding included, and `*` fills the rest of its field with `?`, so nothing may follow it in its field. So `*.*` matches every file, `*.TXT` every file with extension `TXT`, `A*.*` every name starting with A, and `*` alone every file with no extension.

A **volume label** is one packed field of 0 to 16 characters from the same set, with no extension.

### oz3dsk

`oz3dsk` is the command line tool for disk images: it makes and formats them, and copies files on and off them from the host. Images use the `.ozd` extension. The image comes first, then the command, so a line reads "on this disk, do this":

    oz3dsk <image> <command> [<arguments and flags>]

For example, to make a disk of a 1.44 MB floppy's size, and copy a program onto it:

    oz3dsk work.ozd new 720K
    oz3dsk work.ozd format --label WORK
    oz3dsk work.ozd put hello.oz3
    oz3dsk work.ozd dir *.OZ3

| Command   | Arguments and flags                                          | What                                                                                                                                                    |
| --------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `new`     | `<size>`                                                     | Creates a blank image of the size: an unformatted disk. Fails if the image exists, so a mistyped name never blanks a disk                               |
| `format`  | `-c`, `--cluster <sectors>`; `-l`, `--label <label>`         | Formats the disk as the drive's `FORMAT` does, erasing it. Without `--cluster`, the drive's choice (see [Layout](#layout)), and without `--label`, none |
| `info`    |                                                              | Shows the medium (its size and write protection) and the file system (its label, cluster size, clusters, and free clusters)                             |
| `dir`     | `[<pattern>]`; `-a`, `--all`                                 | Lists each file's name, size in words, attributes, and modified time. `--all` lists hidden files too                                                    |
| `put`     | `<host file> [<name>]`; `-t`, `--text`                       | Copies a host file onto the disk, replacing any file of that name. Without a name, it takes the host file's                                             |
| `get`     | `<name> [<host file>]`; `-t`, `--text`                       | Copies a file to the host. Given a folder, it writes the file there, named as on the disk, and without a host file, in the current directory            |
| `del`     | `<pattern>`                                                  | Deletes every file it can that matches, hidden ones included, naming each it can't. Fails if any failed or none matched                                 |
| `ren`     | `<name> <new name>`                                          | Renames a file                                                                                                                                          |
| `attrib`  | `<name>`; `-s`, `--set <letters>`; `-c`, `--clear <letters>` | Sets or clears `r` (read-only) and `h` (hidden), then shows them. With neither flag, only shows them                                                    |
| `label`   | `<label>`                                                    | Sets the volume label                                                                                                                                   |
| `protect` | `on` or `off`                                                | Sets the image's write protection. A read-only image file is always write protected, so turning it off fails                                            |
| `check`   | `-f`, `--fix`                                                | Checks the file system for problems, naming each it finds, and with `--fix` repairs them                                                                |

`info` and `dir` show, for example:

    Size:     720K words (2880 sectors)
    Protect:  off
    Volume:   WORK
    Cluster:  256 words (1 sector)
    Clusters: 2867
    Free:     2864 (716K words)

    HELLO.OZ3              150  --  2026-11-17 10:30
    HELLO.TXT                6  r-  2026-11-18 09:05

* **Sizes** are in words, with an optional `K` (1,024 words) or `M` (1,048,576 words) suffix, and must be a whole number of sectors. So `720K` is 2,880 sectors.
* **Names** on the disk are written with their dot, such as `HELLO.OZ3`, in any case (see [Names and patterns](#names-and-patterns)). `put` of a host file whose name isn't a disk name needs a name given.
* **Patterns** for `dir` and `del` are the host's, not the drive's: `*` matches any characters, the dot included, in any case, and there is no `?`. So `*.OZ3` matches every file with the extension `OZ3`, and `*` every file. `dir` with no pattern lists every file, but `del` needs one, so a missing argument never empties a disk.
* **Binary** is the default: each word is two host bytes, low byte first, as in [program files](2.4-Program-Files.md), so a `.oz3` copied onto a disk is the same program there. A host file of an odd number of bytes ends in a word with a zero high byte.
* **Text (`--text`)** is in the same byte order, since packed text is low byte first too, so only line endings and padding change. Going in, each CRLF and lone CR becomes LF (0Ah). Coming out, zero bytes are dropped, such as the padding at the end of an odd length, and lines stay LF.
* **Attributes:** `put` and `get` keep read-only and hidden where the host has them, with or without `--text`. So a copy of a read-only file stays read-only, and neither replaces a read-only file.
* **Times:** a file copied onto the disk is stamped with the host's local time as it is copied, and `get` leaves the host file's time as the host sets it, so copies don't keep file times. `dir` shows each file's modified time to the minute, in the host's local time, and none for a file with no date.
* **Paths** are written the operating system's way, absolute or relative to the current directory.

`oz3dsk --help` (or `-h`) describes the commands, and `oz3dsk <image> <command> --help` a command's arguments and flags. On success, `oz3dsk` writes what the command shows and exits with 0. A command line it can't run, such as one missing an argument, with a bad size, label, or letters, or naming a host file `put` can't find, prints the problem and exits with 2, without touching the image. Any other failure prints what failed and exits with 1, naming the image (`work.ozd: write protected`), the file on the disk (`work.ozd: HELLO.TXT: not found`), or the host file. `check` succeeds whatever it finds, so a disk with problems still exits with 0.

#### In a host application

A host application reaches the files on a disk image as any others, through Game Bits' `gb::FileSystem`. `DiskFileProtocol` (in `oz3/tools/disk_file_protocol.h`) is a file protocol over a mounted image, registered as `ozdisk` unless given another name, so its paths look like `ozdisk:/HELLO.OZ3`. `Mount` gives it a `DiskImage`, and `Unmount` commits every open file and hands the image back. The protocol lists, reads, writes, deletes, and renames files, reports and sets read-only and hidden, and stamps the files it writes from a clock it is given, reporting each stamp as the file's modified time. Its bytes are `oz3dsk`'s binary, so `WriteProgramFile` and `ReadProgramFile` (see [Program Files](2.4-Program-Files.md)) write and read program files on a disk unchanged, and the [program assembler](2.5-Program-Source.md#assembling-a-program) reads source from one. Formatting, the label, the medium, and free space are on the protocol itself (`Format`, `SetLabel`, `GetMedia`, and `GetVolumeInfo`). `DiskTextFromHost` and `HostTextFromDisk` (in `oz3/tools/disk_transfer.h`) convert text as `--text` does, and `DiskTool` (in `oz3/tools/disk_tool.h`) runs every `oz3dsk` command on any `gb::FileSystem`.

### Ports

| Port   | Use                                                         |
| ------ | ----------------------------------------------------------- |
| First  | Command: command words, arguments, statuses, and results    |
| Second | Data: the words of a file being read or written             |
| Third  | Control: the drive's state when read; requests when written |

The command and data ports use the OZ-3's port handshake. A write ([`OUTS`](2.2-Default-Instruction-Set.md#outs), [`OUTR`](2.2-Default-Instruction-Set.md#outr)) succeeds only when the port's status is clear, and sets it, and the drive takes the word and clears the status. A read ([`INS`](2.2-Default-Instruction-Set.md#ins), [`INR`](2.2-Default-Instruction-Set.md#inr)) succeeds only when the status is set, and clears it, and the drive puts the next word there. Each port holds one word or dword at a time, so a word waiting there can't be skipped or overwritten. The drive takes a word, or puts the next one in its port, the cycle after a core reads or writes the port, before the next instruction can.

#### The control port

The drive keeps the control port's value, its **state word**, current without setting its status, so `IN` reads the drive's state at any time and disturbs nothing.

| Bits | Field   | What                                       |
| ---- | ------- | ------------------------------------------ |
| 0–3  | Phase   | Where the current command is, below        |
| 4    | Disk    | 1 if a disk is in the drive                |
| 5–7  | —       | Reserved                                   |
| 8–15 | Command | The current command's code, or 0 when idle |

| Phase | Meaning                                    |
| ----- | ------------------------------------------ |
| 0     | Idle: waiting for a command word           |
| 1     | Arguments: waiting for more argument words |
| 2     | Working: busy, with nothing to send yet    |
| 3     | Sending: words waiting on the command port |
| 4     | Reading: streaming data to the data port   |
| 5     | Writing: taking data from the data port    |

The state word changes only after what it describes has happened on the ports, so it can lag behind them, but never run ahead.

**Requests:** the OS writes a request word with `OUTS`, setting the port's status. The drive acts on each bit, then restores the state word and clears the status in the same step. Bit 0 is **reset**, and the others are reserved: a request of 0 does nothing.

**Reset** abandons the current command, silently (see [Aborts](#aborts)), withdraws any word waiting on the command and data ports, clearing both ports' statuses, and returns the drive to idle. It works in every phase, so it is the one sure way back to a known state. A reset is:

1. `OUTS` 1 to the control port.
2. [`TSTP`](2.2-Default-Instruction-Set.md#tstp) the control port until **S** is clear. The reset is done, the drive is idle, and the state word is current.

A request that arrives while the disk is busy waits in the control port until the disk is done (see [Timing](#timing)), so `TSTP` shows it pending until then.

Don't `IN` the control port while a request is waiting: `IN` clears the status, which would hide the request. That is also why a reset is waited for with `TSTP` rather than a bit in the state word.

### The command protocol

A **command word** holds the command's code in its high byte and a **handle** in its low byte, or 0 for a command without one. A handle is a slot, 0 to slots − 1, and FFh means every slot, for `CLOSE` only. Each command takes a fixed number of argument words, and returns a fixed number of results after an OK status, so the OS and the drive never disagree about where a command's words end. A status other than OK ends the command's words on the command port: no results or completion follow it. The only words that can come after one are on the data port, when a transfer fails partway (see [Early completion](#early-completion)).

Each field moves in its natural width: a word field (a command word, a status, a count) is a word in port word 0, a dword field (a position or a size) is a dword with the low word in word 0, and an 8-word field (a name, a pattern, or a label) is 4 dwords, and a 16-word directory entry 8, with the lower-numbered word of each pair in word 0.

The drive always moves both of a port's words, as a dword instruction does, whatever a field's width: word 1 of a word field it sends is 0, and it ignores word 1 of a word field it takes. So an OS may move a word field with either width.

A command runs in up to three steps:

1. **Accept.** The OS writes the command word and its arguments. The drive checks everything it can without the disk, and puts a status on the command port, with no interrupt. An error ends the command. A **synchronous** command puts its results here too, and ends.
2. **Data.** For reading and writing only: the words of the transfer move through the data port.
3. **Completion.** For a **latent** command: the drive does the work on the disk, then puts its completion status and any results on the command port, and **raises its interrupt**.

**Waiting for idle:** before writing a command word, the OS reads the control port until the phase is 0. A command ends only once the drive sees that the OS has taken its last word, the next time the drive runs, which may be after disk work the host started, such as reading a disk just inserted. Until then the phase shows 3, and a command word written meanwhile would look to the drive like its own last word, not yet taken.

**Waiting for the accept status:** the command port's one status serves both directions, so right after the OS writes a command's last word, the status is still the one its word set, and an `INS` would read that word back as if it were the status. So after its last word, the OS reads the control port until the phase is 2 or higher, which means the drive has taken the word. Only then does it read the command port. Later reads in the same command don't need this, as the status is then only ever set by the drive.

**The interrupt** has one meaning: the current command's completion is ready. Only one command is ever in flight, so it always belongs to the last command the OS issued. An OS can [`WAIT`](2.2-Default-Instruction-Set.md#wait) after a latent command's accept, and let the drive's interrupt handler wake it.

**Moving words:** `OUTR` and `INR` suit every step. The OS lays out a command's words in memory, and sends each run of fields with the matching width, such as a name with one `OUTR.ID` of 4 dwords, and reads results the same way, such as a directory entry with one `INR.ID` of 8 dwords. Each stops when the port isn't ready, and sets **S** only once R7 reaches 0, so a loop of the instruction and a jump on **S** is enough for arguments and results, which the drive always delivers in full once started. The data step needs one more check (see [Reading and writing](#reading-and-writing)).

#### Aborts

Only a reset abandons a command. A command word never does: the drive reads the command port only while it waits for a command's words, so in other phases a word the OS writes there doesn't start a command.

* **Phases 2, 4, and 5:** the OS's `OUTS` succeeds, as the port is empty, but the drive isn't reading it, and the word is lost when the drive puts its completion's status there.
* **Phase 3:** a word from the drive is waiting, so `OUTS` fails with **S** clear. The OS reads the waiting words first, or resets. Never `OUT` to the command port, which would replace the drive's word without the drive knowing.
* **Phase 1:** the drive takes the word as the command's next argument, since nothing tells the two apart. A confused OS that stops partway through a command's arguments is what reset is for.

A reset has these outcomes:

* **Statuses and results** not yet read are dropped.
* **An interrupt** the drive has already raised for a completion stays raised, so the OS's handler still sees it.
* **A read** stops, and the handle's position is just past the words the OS actually took.
* **A write** keeps the words the drive has taken, as if the write had been for that many, and the size grows to cover them. A word still waiting in the data port is dropped.
* **Any other latent command** finishes its disk work, so a change is never left half done, and its completion is dropped.

The OS can check what happened afterward, with `INFO` or `FIND`.

#### Timing

Only the disk takes time: reading a sector costs its words at the read rate, or at the cache rate if it is in the read cache, and writing one costs its words at the write rate. A transfer that isn't the next sector after the one before, in the same direction, first costs the latency, and so does the first. Reads from the cache move nothing, so they don't change which sector is next. Moving words through ports, and the drive's own checks, take no time.

The drive is busy while the disk is: once it has done some disk work, it does nothing else until the time that work took has passed. It takes no words, sends no words, and handles no requests, not even a reset, as a real controller can't stop a sector partway either. So a command that arrives while the disk is busy, such as reading the superblock of a disk just inserted, waits in the command port until the disk is done.

A latent command's disk work starts once the OS has read its accept status, and the drive shows phase 2 until it is done. Then it posts the completion, and raises its interrupt.

The drive holds a sector for each slot, one directory sector, and two FAT sectors, one of which is always sector 1, where the free list's head is. Before a buffer takes another sector, the drive writes it if it has changed. So a big directory is slow to search, as its sectors pass through one buffer, though the read cache softens a second pass.

#### Committing

The sectors the drive holds are the only changes not yet on the disk, so a **commit** is the drive writing them. It happens at known points:

* **Every command that changes a directory** (`CREATE`, `DELETE`, `RENAME`, `ATTRIB`, `LABEL`, and `FORMAT`) commits before it completes.
* **`CLOSE`** of a file written since its last commit writes its data, the FAT, and its directory entry, stamped with the clock. A file only read, and a directory, write nothing.
* **`FLUSH`** does the same as `CLOSE`, keeping the file open.
* **`TRUNCATE`** commits as `FLUSH` does, with the file's new size, then frees its clusters.
* **`WRITE`** doesn't commit, so a run of writes isn't charged a commit each time. Its data reaches the disk as the file's sector moves on, but its size only at `FLUSH` or `CLOSE`.

The drive orders its writes so a crash can't cross-link files: a cluster comes off the free list on disk before anything links to it, and is unlinked from everything on disk before it joins the free list, and a file's data is on the disk before the size that covers it. The worst a crash can leave is clusters no file or free list has, which a check of the disk can reclaim.

An open file's size is in its slot until it is committed, so a listing shows an open file as it was last committed. A program that wants a listing to show its progress flushes.

#### The free count

The drive keeps a count of the free clusters, never on the disk. The first command after a disk is inserted that needs it counts them by walking the whole free list, which is slow on a big, scattered disk, as DOS's was. From then on, the drive keeps it current as it allocates and frees. `OPEN`, `CREATE`, `VOLUME`, and `FORMAT` need it, except an `OPEN` on a write-protected disk, so every file is open with the count known, and a `WRITE` can work out at accept how much fits, without the disk.

#### Disks coming and going

* **Inserting** a disk reads its superblock, as disk work, so the drive is busy until it is done (see [Timing](#timing)). The disk bit shows once it is.
* **Ejecting** a disk discards everything the drive hadn't written to it, as pulling a real floppy would. Every open slot becomes **stale**. Nothing else changes for a command in progress: a latent command whose disk work is done completes with the status that work had, and one whose work hasn't started finds no disk when it does. A transfer's next word fails with **disk changed** (see [Early completion](#early-completion)).
* **Stale slots:** every command on a stale slot fails with **disk changed**, except `CLOSE`, which frees the slot. It succeeds, unless the file was written since its last commit, when it fails with **disk changed**, as those writes are lost. So a program can't write into a different disk by accident.
* **Failing:** once the host fails to read or write the disk, every command fails with **I/O error**, except `CLOSE`, which still frees the slot. Ejecting the disk and inserting it again is the retry, leaving the disk as a crash at the failure would.
* **Shutting down:** when the machine is shut down cleanly, the drive commits every file, so the disk stays consistent.
* **Nothing else** may change a disk while it is in a drive, such as a tool on the host: the drive assumes it is the only writer.

### Commands

Codes are grouped by kind, with the low nibble numbering commands within a group. Code 0 is never a command, so the control port's command field reads 0 when idle. An unknown code fails at once, after the command word alone, with **bad command**. "h" marks a command that takes a handle in its command word's low byte, and a number after a field is its size in words, where it is more than one.

#### Files

| Code | Command     | Arguments | Accept | Completion     |
| ---- | ----------- | --------- | ------ | -------------- |
| 10h  | `OPEN`      | name (8)  | status | status, handle |
| 11h  | `OPEN ROOT` | —         | status | status, handle |
| 12h  | `CREATE`    | name (8)  | status | status, handle |
| 13h  | `CLOSE h`   | —         | status | status         |
| 14h  | `FLUSH h`   | —         | status | status         |

* **`OPEN`** opens a file in the root directory, in the lowest free slot, and gives the slot as its handle, at position 0. It fails with **not found**, or with **in use** if the file is already open, as two slots on one file would clobber each other.
* **`OPEN ROOT`** opens the root directory as `OPEN` does a file, as a **directory handle**, which reads the directory's entries and lists them with `FIND`. The root is open in at most one slot, like any file.
* **`CREATE`** makes an empty file, stamped with the clock, and opens it. It fails with **exists** if the name is taken: to replace a file, delete it first. It fails with **disk full** if the directory has no free entry and can't grow.
* **`CLOSE`** commits the file if it was written, and frees the slot, even when it fails. With h = FFh it closes every open slot, and completes with the first failure, if any. Closing a slot with nothing open is **bad handle**, but h = FFh is fine with none open.
* **`FLUSH`** commits the file, keeping it open (see [Committing](#committing)). On a directory handle it does nothing, and succeeds.

#### Data

| Code | Command          | Arguments    | Accept                         | Data               | Completion             |
| ---- | ---------------- | ------------ | ------------------------------ | ------------------ | ---------------------- |
| 20h  | `READ h`         | count        | status, n                      | OS reads n words   | status, words read     |
| 21h  | `WRITE h`        | count        | status, n                      | OS writes n words  | status, words written  |
| 22h  | `READ PACKED h`  | count        | status, n                      | OS reads n dwords  | status, dwords read    |
| 23h  | `WRITE PACKED h` | count        | status, n                      | OS writes n dwords | status, dwords written |
| 24h  | `SEEK h`         | position (2) | status                         | —                  | —                      |
| 25h  | `INFO h`         | —            | status, position (2), size (2) | —                  | —                      |
| 26h  | `TRUNCATE h`     | —            | status                         | —                  | status                 |

* **Counts** are 0 to 65,535 words, or dwords for the packed commands. The reads and writes are described in [Reading and writing](#reading-and-writing). A directory handle can be read, which gives its raw entries, but not written.
* **`SEEK`** and **`INFO`** are synchronous. `SEEK` moves the handle's position anywhere from 0 to its size, and fails with **past end** beyond it. The next transfer finds the position on the disk, charging the time then.
* **`TRUNCATE`** sets the file's size to its position, and frees the clusters past what that size needs. As `SEEK` can't pass the end, it only ever shrinks a file: truncating to empty is `TRUNCATE` at position 0. It commits before it completes, as clusters it freed only in memory could be taken by another file, which a crash would leave cross-linked. The words past the new size in its last sector aren't cleared, but nothing reads past the size.

#### Directory

| Code | Command  | Arguments                  | Accept | Completion         |
| ---- | -------- | -------------------------- | ------ | ------------------ |
| 30h  | `FIND h` | pattern (8)                | status | status, entry (16) |
| 31h  | `DELETE` | name (8)                   | status | status             |
| 32h  | `RENAME` | old name (8), new name (8) | status | status             |
| 33h  | `ATTRIB` | name (8), attributes       | status | status             |

* **`FIND`** takes a directory handle and looks from its position for the next entry the pattern matches. It gives the entry as it is on the disk, and leaves the position just past it. At the end it fails with **not found**. `SEEK h, 0` starts a listing again.
* **`DELETE`**, **`RENAME`**, and **`ATTRIB`** fail with **not found**, or **in use** if the file is open.
* **`DELETE`** frees the file's entry, then its clusters. It fails with **read-only** on a read-only file.
* **`RENAME`** changes only the entry's name, keeping its modified time. It fails with **exists** if the new name is taken, even by the file itself.
* **`ATTRIB`** sets read-only and hidden (bits 0 and 1), keeping the entry's other bits. Any other bit is **bad attributes**.

#### Disk

| Code | Command  | Arguments                      | Accept                          | Completion                                                           |
| ---- | -------- | ------------------------------ | ------------------------------- | -------------------------------------------------------------------- |
| 40h  | `MEDIA`  | —                              | status, sector count (2), flags | —                                                                    |
| 41h  | `VOLUME` | —                              | status                          | status, label (8), sectors per cluster, cluster count, free clusters |
| 42h  | `FORMAT` | label (8), sectors per cluster | status                          | status                                                               |
| 43h  | `LABEL`  | label (8)                      | status                          | status                                                               |

* **`MEDIA`** is synchronous, and describes the medium from the image's header: its sector count, and its flags word, with bit 0 set if it is write-protected. It works on an unformatted disk.
* **`VOLUME`** describes the file system. Its free clusters come from the free count, so it is quick unless it is the first command to need it (see [The free count](#the-free-count)).
* **`FORMAT`** makes a new, empty file system over the disk's whole sector count, labeled and stamped with the clock. Sectors per cluster is a power of two from 1 to 64, large enough that at most 65,534 clusters cover the disk, or 0 for the drive to pick the fewest that do; any other is **bad argument**. It fails with **in use** if any slot is open, stale slots aside. A format that fails partway leaves the disk unformatted. It works on an unformatted disk.
* **`LABEL`** changes the volume label.

#### Where errors are found

The accept finds everything it can without the disk, checking in this order:

1. The arguments, in the order they arrive, starting with the handle in the command word: **bad handle**, **disk changed**, **I/O error**, and **wrong handle type** for the handle, then **bad name**, **bad pattern**, **bad label**, **bad attributes**, and **past end**.
2. The disk, for a command with no handle: **no disk**, **I/O error**, **write protected** for a command that changes the disk, then **unformatted** for one that needs a file system (all but `MEDIA` and `FORMAT`). The drive knows whether the disk is formatted from reading its superblock when it was inserted.
3. What the command needs: **read-only** and **write protected** for a handle that is written or truncated, **too many open**, **in use** and then **bad argument** for `FORMAT`, whose sectors per cluster depend on the disk's size, and **disk full** for a `WRITE` with no room for a single word (or dword).

The completion finds everything that needs the disk: **not found**, **exists**, **in use**, **read-only** for `DELETE`, **disk full**, **corrupt**, **I/O error**, and **no disk** if the disk was ejected before the work ran.

### Reading and writing

#### Reading

An example: handle 1 is open on a 300-word file at position 0, and the OS asks for 500 words.

1. The OS writes `READ` with handle 1, then the count, 500, to the command port.
2. The drive works out n, the lesser of the count and the words left in the file: 300. This needs no disk. The OS reads OK, then 300, from the command port. No interrupt.
3. The drive reads the sector holding the position, charging the latency if it isn't the next sector, and the sector's time. The data port stays empty meanwhile.
4. The drive streams that sector's words through the data port, each ready before the OS asks. Then it reads the next sector, and the port goes quiet again, then streams its words, and so on up to word 299. The drive reads each word while the one before waits in the port, so the next sector's read overlaps the OS taking the last word of the one before.
5. Once the OS has taken the last word, the drive puts OK, then 300 words read, on the command port, and **raises its interrupt**.

The handle's position is now 300. A count of 0, or a position at the end, gives n = 0, with no data step and an immediate completion.

#### Writing

An example: handle 2 is a 500-word file positioned at its end, the OS writes 100 words, and clusters are one sector.

1. The OS writes `WRITE` with handle 2, then the count, 100, to the command port.
2. The drive works out n without the disk: the file's last cluster has room for some of the words, the rest needs one more cluster, and the free count says there is one. n is the words that fit, here all 100. The OS reads OK, then 100, from the command port.
3. The drive takes the OS's first word from the data port as soon as it arrives. Position 500 is partway into a sector, so it reads that sector, keeping its other words, and takes no more words until that is done. The OS's next `OUTS` waits meanwhile: the drive stalls the OS just by not taking the word in the port.
4. The drive takes words until the sector is full. The next word is the first of a new cluster, so as it takes it, the drive allocates the cluster, reading the FAT sectors that takes, and writes the full sector as its buffer moves on to the new one. It takes the rest, up to word 99, once that disk work is done. The new sector and the FAT's changes stay in the drive until it needs their buffers, or the file is committed (see [Committing](#committing)).
5. The slot records the new size, 600. The drive puts OK, then 100 words written, on the command port, and **raises its interrupt**.

As n comes from the free count, which only this drive changes, n is a promise. If only some of the count fits, the accept is OK with a smaller n, the OS sends only n words, and the completion is **disk full**. If none fits, the accept fails with **disk full**. A count of 0 is OK, with n = 0. A cluster is allocated only when its first word arrives, so after a reset or a failure there is nothing to free.

Writing before the end overwrites, needing no allocation unless the write runs past the end. Files only grow by writing at or across their end.

#### Early completion

If something fails partway through a transfer (a broken chain, a host I/O error, or the disk ejected), the drive posts the completion at once, before the data step is over: the error status alone, since an error carries no more words, and **raises its interrupt**. A write first commits what it has taken. The handle's position, which `INFO` gives, shows how much really moved. Nothing more moves on the data port until the status is on the command port. Until the OS reads it, the control port shows phase 3, and then phase 4 (or 5 for a write) again until the data step ends.

The data step still honors n, so the OS's loop never hangs: the rest of a read comes through as zeros, and the rest of a write is taken and thrown away. These words take no disk time. The OS may run its loop to the end and then read the status, or read the status first and then cut the loop short with a reset.

The OS can notice a failure early, at no cost on the fast path. Its loop on the data port only stalls at sector boundaries, and only then does it check the control port:

1. Set R7 to n, and point R4 or R5 at the buffer, which puts it in the EXTRA bank, so the buffer can be the calling program's memory.
2. `INR` from the data port (or `OUTR` to it, for a write).
3. If **S** is set, all n transfers are done, and the completion is on the command port.
4. Otherwise, `IN` the control port. Phase 4 (or 5) means the drive is reading or writing a sector, so go back to step 2. Phase 3 means a completion is waiting, so the transfer failed: read the status, then finish the loop, or reset.

#### Packed transfers

`READ PACKED` and `WRITE PACKED` work exactly as `READ` and `WRITE`, but in dwords. Each transfer on the data port carries two words, the low word in word 0, for the dword forms of `INR` and `OUTR`, and the count, n, and the completion's count are all in dwords, so they match the OS's loop count directly. Positions and sizes are still in words.

* **Reads:** n is the lesser of the count and the dwords the rest of the file needs, rounded up. If an odd number of words is left, the last dword's high word is 0, and the position stops at the file's size.
* **Writes** are always whole dwords, so a file of odd length ends with a `WRITE` of its last word.

### Using the drive

These sketches show one way an OS could use the drive. They aren't part of the drive, and an OS is free to differ.

* **Owning the drive:** one OS core issues every drive command, so only one is ever in flight. Programs ask through OS calls, which wait in a queue while the drive is busy. The OS maps its own file handles onto the drive's slots, so it decides who may use which file.
* **A program reads a file:** the OS looks up the file's slot, and sets its EXTRA bank to the program's bank. It waits for phase 0, sends `READ` with the slot and count, waits for phase 2 or higher, and reads the status and n. It then loops on `INR` into the program's buffer as in [Early completion](#early-completion), reads the completion, and wakes the program.
* **Commands with no data,** like `OPEN` or `DELETE`, let the OS `WAIT` after the accept, for the drive's interrupt handler to wake it when the completion is ready.
* **Listing a directory:** `OPEN ROOT`, then `FIND` with a pattern again and again until **not found**, then `CLOSE`. Each `FIND` gives a whole entry, so a listing shows names, sizes, attributes, and dates without reading the directory itself. An OS can also `READ` the directory and match its entries itself.
* **Loading a program:** open the [program file](2.4-Program-Files.md), read its header with `READ`, then read each section straight into its bank with `READ PACKED` and the dword form of `INR`, which halves the instructions a word.
* **Disk changed** means the slot's disk is gone: the OS closes the slot, which frees it, and tells the program that owned the file. A `CLOSE` that fails this way means the file's last writes never reached the disk.
* **I/O error** means the disk has failed: the OS closes its slots and reports it, and the disk works again once it is ejected and inserted.
* **A lost OS,** such as after a fault in its drive code, resets the drive and issues the command again. The control port's phase shows whether that's needed.
